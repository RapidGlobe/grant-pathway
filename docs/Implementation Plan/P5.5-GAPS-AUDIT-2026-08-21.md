## What this audit established without needing a decision

**`GAP-27` is largely obsolete.** It was written on 2026-06-04, before Axiom existed on this project. Axiom has since supplied the evidence that closed `GAP-108`, timed `GAP-115` three times, and proved a negative for `RT-16`. Reviewing the row as written would overstate what is missing; the genuine remainder is **alerting**, not observability.

**`GAP-03` got cheaper and more relevant on the same day.** `GAP-115` option (b) raised `maxDuration` from 90 to 180 on `/api/generate-summary`. So the timeout ceiling moved, and the alert that would tell anyone it was being approached still does not exist. These two rows should be decided together.

⚠️ **`GAP-111`'s cookie count could not be reproduced from outside the browser, and this changes what the amendment must say.** Unauthenticated requests to `https://grantpathway.org.uk/` and `/privacy` return **HTTP 200 with no `Set-Cookie` header at all**. The finding was made in a browser, so the additional cookies are most likely set by client-side JavaScript or by Vercel's edge features rather than by the application server.

**That distinction matters for the wording, not for the validity of the finding.** A cookie the app sets, a cookie Vercel sets, and a cookie set by a script in the page are three different things to declare, and Section 9 currently describes only the first. **Before drafting the amendment, capture the actual cookie list from a browser** — name, who sets it, purpose, lifetime — because the policy has to categorise them, not just count them. Doing this from `curl` would produce a policy that is wrong in a new way.

## AUDIT EXECUTED — outcome, 2026-08-21

WJ took every recommendation in section A. **What follows is what actually happened when each was acted on**, which diverged from the plan above in three places worth reading.

### ⚠️ The audit's most useful catch: its own top-ranked item was already done

**`GAP-109` and `GAP-111` were closed on 2026-08-17, four days before this audit ranked them as the highest-value decision.** Both register rows still read 🔴 No task.

Going to draft the amendment found it published. `privacy-policy-external.md` — the file the live `/privacy` page renders — already lists **Upstash** in the processor table (_"Limits how often requests can be made, to protect the service from abuse"_, Ireland, EEA), and Section 9 already carries **two** cookie bullets where it carried one. Both landed in **v1.7**; the documents are now at **v1.9**. Axiom was added in the same pass.

**The lesson is about the register, not the policy.** A stale row does not merely waste time here — acting on it would have produced a **duplicate amendment to a solicitor-reviewed legal document**, the one artefact in this project that costs a fee to review. `AGENTS.md` §3 Step 2a exists because that document keeps drifting; this is the opposite failure, and it is just as expensive.

Both rows are now 🟢 Built, with the evidence recorded in each.

### ⚠️ `GAP-119` raised, High — found by accident, and it is a launch blocker

While trying to re-capture the cookies for `GAP-111`, a browser pointed at **`https://grantpathway.org.uk`** landed on `/lander` and returned:

> grantpathway.org.uk is parked free, courtesy of 123 Reg.

**The service has no working public address.** The domain is attached to the Vercel project — apex and `www`, added 2 July 2026 — but its nameservers were never moved: `vercel domains inspect` shows intended `ns1/ns2.vercel-dns.com` against current `ns39/ns40.domaincontrol.com`, both flagged mismatched. `vercel alias ls` lists only per-branch preview aliases; **there is no production alias at all.**

**Three consequences.** The advertised address shows a parking page with third-party ad links. That page sets its own cookies before any consent — including **`caf_ipaddr`, the visitor's IP address** — on a page where Grant Pathway's privacy policy is not served and cannot be. And anything building a link from the site URL, which includes `FR-44`'s verification and password-reset emails, would point users there.

**Why nothing caught it, which matters more than the fault.** Every `P5.5` production test — both flagships, the regression suite, the load test, `RT-14`/`RT-15`/`RT-16`, and this morning's `GCM-01` — ran against the `*.vercel.app` deployment URL while signed in to Vercel. **Those results all stand: they exercised the real application against the real production database.** What has never been exercised is the **public entry point**, because no test names it. `RT-00` step 1 tells the tester to use "the test URL" without pinning what it should be. Fifty days passed.

### Two smaller corrections to this document's own analysis

**The cookie note in v1.0 was measured with the wrong instrument.** It reported that production returns HTTP 200 with no `Set-Cookie` header. Those requests hit the **123 Reg parking page**, not the application — so the observation was true and meaningless. **The conclusion drawn from it, that Section 9 needed re-categorising, was also unnecessary**: the cookie detail was in the `GAP-111` row all along (three Supabase PKCE code-verifier cookies, none HttpOnly, set before authentication completes), captured by WJ in DevTools on 2026-08-17.

**A re-capture is now impossible anyway**, and this is worth knowing before someone plans it: the public domain is parked, and the working deployment sits behind Vercel SSO. **There is no reachable public instance to inspect.** WJ's original capture remains the only one.

**`GAP-32` is further along than its row says.** Item **C** — the PRD's `FR-22` hedge, the one place still legitimately carrying the retired "never store guidelines" wording — was **rewritten on 2026-08-15**, when `P5.4` applied the fourteen dev-only migrations to `grant-pathway-prod`. Its blocker cleared and the row was not updated. Only item **B** remains: two ADR notes (`ADR-ARCH-004`, `ADR-FILE-004`) drafted and unsigned.

### Check 1 — Reconcile the ADR consequence tables against the gaps register

The two halves of `ADR-TRACEABILITY.md` carry statuses for the same gaps and are maintained separately, so they drift. **On 2026-08-06 `GAP-01`, `GAP-02` and `GAP-04` read ⚠️ in the ADR tables and ✅ built in the register.** ⚠️ **The ADR-table half is the half `AGENTS.md` §2 sends every session to before starting work**, so a stale ⚠️ there costs time on every future task, not just once.

**Method:** for every gap id, compare its status in the ADR consequence tables against its register row. Report every disagreement rather than silently picking the newer one — which is right is a judgement, and the register is not automatically the winner.

### Check 2 — Confirm the Task column still points somewhere real

The 2026-07-30 restructure moved work between tasks without updating the register. **Known already:** `GAP-21`, `GAP-22` and `GAP-23` read `P5.3` when they belong to `P5.3b`; `GAP-12` read `P5.4` when the `v1.0.0` tag moved to `P5.6`. **And `GAP-119` was found today with no task at all when `P5.6` covered it.**

**Method:** for every row with a Task value, confirm that task still exists under that identifier in `IMPLEMENTATION-PLAN.md` and still describes the work. **A row pointing at a task that has moved is worse than a row pointing at nothing** — it reads as covered.

### Check 3 — Every ⚠️ row in the ADR consequence tables has a matching register row
