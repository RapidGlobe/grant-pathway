## Running order

The order matters. Steps 1–4 are prerequisites; 5–8 are safe any time; 9–13 touch production for the first time; 14 is the exit test.

### Phase D — Observability, then the exit test

**13. Sentry, all in one sitting** — **five** jobs, one visit (the fifth added 2026-08-16 from step 7):

> ✅ **`GAP-107` fixed and verified 2026-08-16 — these four jobs are no longer gated.** Sentry's `environment` tag was set from `NODE_ENV`, which Vercel reports as `production` for **preview** builds too, so a rule scoped to production also matched preview traffic. `lib/sentry-environment.ts` now resolves it from `VERCEL_ENV`, proven by a build that inlines `environment:"preview"` into the client chunk. **Scope the two alert rules below to `production` and it now means what it says.**

- **New-issue alert rule.** Seven production issues accumulated unnoticed; that is what an absent alert rule looks like.
- **AI route performance alert (`GAP-03`).** P95 > 75s on `generate-summary` (before its 90s limit), > 50s on `refine-answer` (before its 60s). Needs a production baseline, so set it after the first successful deployment.
- ✅ **Confirm PII scrubbing is active at runtime — DONE 2026-08-16, and it passed as a _positive_ test.** The code half was verified in `P5.2`; what was missing was seeing a real event arrive with the fields genuinely absent. **Absence alone would have proved nothing**, since an ordinary error need not carry those fields at all — so a temporary route planted every scrubbed field with unmistakable canary values and captured a tagged exception. Event `ef0934c9aff24368b1fe084e7b7d35f4`: **all four breadcrumb canaries (`guidelinesText`, `answerText`, `path`, `signedUrl`) stripped, no user email or username, and the deliberately-unlisted `keep_this_one` survived.** That last part is what makes it conclusive — `beforeSend` removed exactly the four keys on the list and left the fifth, so it is discriminating rather than simply emptying the breadcrumb.
- ✅ **`GAP-21` — confirm a tagged event actually reaches Sentry — DONE 2026-08-16.** Same event as above, issue `GRANT-PATHWAY-B`, carrying `route`, `step` and `ai_error` tags plus `environment: production` and `release: b7c376a10c05`. **This closes the last item standing between `P5.3b` and unconditional completion.** ⚠️ **The temporary route that produced it (`app/api/debug-sentry/route.ts`) has been deleted** — check it is gone before signing this step off, since a route that writes to the Sentry quota should not outlive the check it was built for.
- **NEW — confirm a release exists in Sentry _with artifacts_ (from step 7).** Releases → the release matching the deployed commit → check it carries uploaded source maps. **`SENTRY_AUTH_TOKEN` being present proves the credential is set, not that the upload succeeded** — the build plugin sets a release name either way, so the release name visible on the live client is not evidence. **Do this one first in the sitting:** if the maps are missing, every stack trace in the other four jobs is minified, and you would be reading them the hard way for no reason.

### Also required, not a step

**Rollback procedure (`GAP-28`)** — document and follow: (1) Vercel → Deployments → last known-good → Redeploy (~60 seconds). (2) Deploy to production only during business hours (09:00–17:00 Mon–Fri) unless responding to a live P1. (3) Before re-deploying after a revert, confirm the root-cause fix is in the branch and tests pass locally. (4) Record the incident and rollback in `CHANGELOG.md`.

**Decide `master`'s branch protection (added 2026-08-15, `ADR-OPS-002` consequence 1).** A ruleset exists — pushes report `Bypassed rule violations: 3 of 3 required status checks are expected`, so the checks are configured and being bypassed rather than satisfied. Entirely reasonable for solo pre-launch work; **not a defect.** But before real users depend on the deployment, either keep the bypass and record why, or drop it so a red CI run cannot reach production.

**Documentation trigger — flip `FR-22` after step 9 lands, not before.** `PRD-Grant-Pathway.md` §6.4 still says guidelines "shall not be permanently stored", qualified as true "of the product as it exists in production today". That qualification is **accurate right now** and stops being accurate the moment the migrations are pushed. Rewrite the row to match `acceptance-criteria.md`'s corrected version and delete the "changing under Phase 6" hedge. `GAP-32`.

## Deliberately not done

**Bedrock hard-stop IAM action — accepted risk, not built. Decision: WJ, 2026-07-30.** The `grant-pathway-bedrock-cap` AWS Budget (~£100/month, alert-only) exists. Automated IAM revocation would guarantee the ceiling but would cut AI off mid-application for every user at once, with no warning. **The real control is the per-user 50-requests-per-month cap in `reserve_ai_slot`**, which bounds spend per user rather than failing the whole service.

**`v1.0.0` tag — belongs at the end of P5.6, not here.** Tagging "after the first successful production deployment" would stamp it before the DNS cutover and before the go-live gate, i.e. before the service was actually live. `GAP-12`.

## Carried into P5.6 — do not lose these

- **Change Supabase's Site URL to `https://grantpathway.org.uk`** at the DNS cutover. It is currently `https://grant-pathway-three.vercel.app`, which is correct for now and wrong the moment the real domain is live. Use Keyword type, looking for `"status":"ok"` on `/api/health`. **Add it rather than re-pointing the existing monitor:** keeping both isolates faults — domain red with Vercel green means DNS or certificate, not the application.
- **Set `NEXT_PUBLIC_ALLOW_INDEXING=true`** on the production domain, and only then — `lib/site-url.ts` makes indexing opt-in precisely so a pre-launch host cannot be indexed by accident.
