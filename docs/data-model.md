# Data Model — Grant Pathway v1

**Tier:** 1 — Always check after every task
**Volatility:** High
**Update when:** Any change to database schema, table definitions, field types, constraints, or entity relationships

This document defines the entities, fields, relationships, and key constraints for all data stored by Grant Pathway v1. It is a reference for the PRD, for development, and for data protection documentation.

All data is stored in PostgreSQL via Supabase (London region). Authentication is managed by Supabase Auth. No persistent data is held at the application layer (Vercel).

## 2. charity_profiles

Stores the charity's full organisational information — the "thick profile" introduced in Mark Two (BD-02). Used as context for all AI-generated content and as a pre-fill source for non-narrative fields on funder forms.

**Implementation note (2026-07-05, revised 2026-07-15):** sections 2.2–2.5 below document the target "thick profile," not all of which has been built. The fields actually persisted in the live `charity_profiles` table and profile-setup form today are: `charity_name`, `registration_number`, `what_charity_does`, `who_charity_helps`, `where_charity_works`, `lookup_source` (2.1/2.3) only. Address/contact (2.2), the remaining financial fields (`accounts_date`, `total_income`, employee/volunteer/trustee counts, salary bands, `government_funding`, `main_non_govt_funders`), and supporting-document status (2.5) remain documented but unbuilt — a pre-existing gap between this document and the codebase, not something P6.1 was scoped to close. The five governance/reserves fields P6.1 added here (2026-07-05) were removed again on 2026-07-15 — never consumed anywhere as `charity_profiles` columns (not by Step 3's summary/eligibility logic, not by P6.5's clone), they were re-sited as `application_items` rows instead. See §4c.

**Key constraints:**

- `status` must be one of the five defined enum values
- `status` transitions follow the rules defined in the application status model
- `mismatch` is a terminal state — no transitions to steps 4 or 5 are permitted from this state (FR-47, DR-EL-001)
- `last_exported_at` is updated on every export, not just the first
- `first_exported_at` is the opposite — set only on the first export, then left untouched by every subsequent export
- Funder guidelines (uploaded file or pasted text) are **not** stored — they are used for AI processing within the session only (FR-22)

**Database functions (added 2026-07-13, repointed to `application_items` by the P6.2 migration `20260714000000`):** approval and re-opening are not plain application-layer `UPDATE` statements -- they run as single-transaction Postgres functions (migration `20260701000000`, a launch-blocker fix for a real bug where `applications.status` could update without `application_items.is_approved`, or vice versa):

- `approve_application(p_application_id, p_user_id)` -- sets `status = 'approved'` and `is_approved = true` on every answer row, in one transaction
- `reopen_application(p_application_id, p_user_id)` -- sets `status = 'in_progress'`, `current_step = 4`, `draft_status = 'in_progress'`, `assembled_draft = null`, and `is_approved = false` on every answer row, in one transaction

### 4b. P6.5 — Reuse Previous Application (private, per-charity, per-funder)

**Built 2026-07-14, `grant-pathway-dev` only.** Originally planned as a shared, curator-approved "playbook" per funder (`ADR-DATA-006`'s Option 3) — during the design walkthrough, WJ challenged that premise directly (why shouldn't a charity applicant be their own curator?), and the feature actually built is simpler and lower-risk: no new table, no curator role, no approval workflow, no versioning.

When a charity starts a new application for a funder they've already reached Step 4 with before (`getPreviousApplicationForFunder`, `actions/applications.ts`), they're offered an explicit choice on Step 1 — start fresh, or start from their own last application to that funder. Choosing reuse (`cloneApplicationForReuse`) copies, entirely within the current user's own rows:

- The question list — every ordinary `application_items` row (`field_key IS NULL`), including their own previous answers, with `is_approved` reset to `false` and `cloned_from_application_id` set to the source application's ID
- The retained guideline text (`application_guidelines.guideline_text`) — a full independent copy, not a shared reference
- The AI summary (`applications.ai_summary`) — so Step 4's prep checklist still has content to show

**The 5 governance items (§4c) are deliberately excluded from this copy** (2026-07-15) — every application collects those facts fresh, no exception for reuse. The new application's own item-sync path creates them blank instead.

Step 2 (guideline upload) is skipped entirely; the application lands on Step 3 with the carried-over AI summary already in place, continuing through the normal flow from there. See `ADR-DATA-006`'s and `ADR-DATA-007`'s 2026-07-14 amendments for the full design history.

**Key constraints:**

- An application cannot be exported (status → `exported`) until the parent `applications.status` is `approved`
- When an approved or exported application is re-opened, `is_approved` on all items is reset to `false` and `applications.status` reverts to `in_progress`
- `item_order` must be unique within an application

**Table-level grants (fixed 2026-07-23, migration `20260723000000_grant_service_role_item_graph_tables.sql`):** this table and `application_guidelines` (§4a) were created (2026-07-14) with `SELECT`/`INSERT`/`UPDATE`/`DELETE` granted only to `authenticated`, never to `service_role` — unlike the four original tables (`users`, `charity_profiles`, `applications`, `ai_usage_log`), which carry full `service_role` privileges granted ad hoc outside any tracked migration. This went undetected until account deletion (`app/api/account/delete/route.ts`, which runs as `service_role`) failed on its very first cascade step with `42501: permission denied for table application_items`. Fixed on `grant-pathway-dev`; **`grant-pathway-prod` remains unpatched** — same outstanding gap as the general schema-drift tracking (`TEST-DASHBOARD.md`).

### 4c. Governance/reserves items (re-sited from `charity_profiles`, 2026-07-15; guideline-driven since PDR-AI-008, same day)

**Built 2026-07-15, `grant-pathway-dev` only (migration `20260715000000`).** The 5 governance/reserves facts P6.1 added to `charity_profiles` (§2.4/2.4a, 2026-07-05) were never actually consumed anywhere — not by Step 3's summary/eligibility logic, not by P6.5's clone — so the `/profile` copy ("helps flag issues before you apply") was untrue. Re-sited as `application_items` rows instead, using the item-graph's previously-unpopulated `number`/`data` item types and `charity_profile` source_of_truth.

**Amendment (2026-07-15, later same day, PDR-AI-008):** live testing of the always-on version below found it disjointed from the rest of Step 4 (no citation, shown regardless of relevance). Reworked the same day: a row is now created only when the AI's guideline extraction actually detects that specific fact being raised (a new `"governanceFacts"` array, `lib/prompts.ts`/`route.ts`) — never all 5 unconditionally. The fixed table below still supplies `item_type`/`is_budget_question`/`item_order`/`item_label` (never trusted from the AI), looked up by `field_key` via `resolveGovernanceInserts()` (`lib/governance-items.ts`) only for whichever facts were actually detected. `guideline_reference` is now populated when the extraction found a citation, exactly like a narrative question/section — no longer always null.

When a fact is detected, its row uses this fixed metadata, identified by `field_key`:

| `field_key`                           | `item_label`                                                                                  | `item_type` | `is_budget_question` | `item_order` |
| ------------------------------------- | --------------------------------------------------------------------------------------------- | ----------- | -------------------- | ------------ |
| `governance_total_expenditure`        | Total annual expenditure (£) (optional)                                                       | `number`    | `true`               | -5           |
| `governance_reserves`                 | Reserves (£) (optional)                                                                       | `number`    | `true`               | -4           |
| `governance_trustees_related`         | Are any of your trustees related to each other by family or business relationship? (optional) | `data`      | `false`              | -3           |
| `governance_bank_signatory_count`     | How many people are authorised as bank signatories? (optional)                                | `number`    | `false`              | -2           |
| `governance_bank_signatories_related` | Are any bank signatories related to each other or to a trustee? (optional)                    | `data`      | `false`              | -1           |

Defined in `lib/governance-items.ts` (single source of truth, imported by both item-sync paths). `answer_text` stores the literal display value as plain text (the number as a string; `"Yes"`/`"No"`/`"Not sure yet"` for the two `data` fields) rather than a coded enum, so `saveAnswer`/`approveAnswer` and the Step 5 Word export need no changes — these rows behave exactly like narrative answers everywhere except the Step 4 input widget (a number input or a Yes/No/Not sure yet select instead of a textarea). The `(optional)` suffix in every `item_label` is deliberate: Step 4's existing `isOptionalQ()` gate already treats any question text containing that phrase as skippable-when-blank, so no change was needed to the approval-gate logic either.

**Created via the same dual sync path every other `application_items` row uses** (`setDraftInProgress`, and the Step 4 page's fallback sync) — both call `resolveGovernanceInserts()` with whichever facts `parsedSummary.governanceFacts` contains this time, independent of `funder_type` (a funder's guidelines can raise these facts regardless of structured/free_form), with `answer_text` deliberately omitted from the upsert payload so a fresh row inserts blank and an already-answered row is never touched on a repeat sync. Orphan cleanup is no longer governance-specific: a previously-created governance item whose fact the extraction no longer detects is deleted if unanswered, kept if already answered — exactly the same rule as a dropped narrative question, since a detected fact's `item_order` is folded into the same `summaryOrders` set (`isOrphanedItem()`'s field_key carve-out was removed).

**No seeding between applications, by design (WJ, 2026-07-15) — unaffected by the guideline-driven rework.** Every application's governance items start blank, every time — including P6.5 reuse, where they are explicitly excluded from the clone (§4b) rather than carried over. Carrying forward financial/governance figures silently was judged a real staleness risk; charities must re-enter and re-attest these facts fresh for every application. There is consequently no single "current value" per charity independent of a specific application — a deliberate trade-off, not an oversight.

**Extraction bar deliberately lower than ordinary "questions."** A fact is extracted whenever the guidelines raise the topic at all — a general eligibility statement or policy requirement counts, not just a discrete question — so an item is shown whenever there's any signal, never withheld pending one precise quotable line. Citation is optional here exactly as it already is for narrative questions/sections (an entry with `citation: null` is still shown, just without a citation badge). If none of the 5 topics are raised anywhere in a funder's guidelines, none of the 5 rows are created — no gap, no placeholder.

**Manual-add fallback for the zero-signal case (built 2026-07-15, same day, migration `20260715000001`).** A new `application_items.added_manually` boolean column (default `false`) is set `true` only when the charity added a governance item themselves via Step 4's manual-add picker, because the extraction found no signal for it — distinguishing it from an AI-detected item with no citation, which otherwise looks identical (`guideline_reference: null` in both cases). Drives an honest "Added by you" badge in Step 4 instead of a citation badge. The picker is scoped to the closed 5-field vocabulary only (never a free-text "add any question" box), offers only the facts not already shown, and is never proactively surfaced — a quiet link, not a suggestion (`PDR-AI-008`). If the extraction later independently detects the same fact (e.g. after a Step 3 regeneration), the ordinary sync's upsert overwrites `added_manually` back to `false` and may populate a real citation — correct behaviour, not a bug, since the fact is then genuinely guideline-derived. New server action: `addManualGovernanceItems` (`actions/applications.ts`).

- `output_mode` is constrained to `generic_export` only (see above)
- `guideline_reference`, when non-null, must match the discriminated-union shape (`source_type = 'page'` requires `page_number` and forbids `heading_path`/`item_number`; `'heading'` requires `heading_path` and forbids the other two; `'item'` requires `item_number` and forbids the other two; `quote` always required)

**R16 resolution:** the `scoring_criterion` item type is how R16 (scoring criteria driven by cross-application funder history, e.g. MK Community Foundation's Group Profile Score) resolves once populated — a visible, non-fillable item flagging that a criterion exists and is outside Grant Pathway's control, never a fillable field. Not yet populated in compatibility mode.

**Predecessor (`application_answers`, superseded 2026-07-14):** the flat model this table replaces also carried `question_type` (added for BD-04, never populated beyond `narrative` in practice — the extraction prompt explicitly discarded non-narrative and conditional questions). A nine-funder review (`docs/BRD plus decisions Mark Two/question-coverage-analysis.md`) found that flat, narrative-only model false in twenty distinct ways (R1–R20), which is what **ADR-DATA-006** (2026-07-05) decided to replace it for.

## 5. ai_usage_log

Tracks every AI API request made by each user. Used to enforce the monthly per-user request limit (50 requests/month) and to monitor running costs (PDR-AI-005).

| Field            | Type      | Required | Notes                                                                                                                                    |
| ---------------- | --------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `id`             | UUID      | Yes      | Primary key                                                                                                                              |
| `user_id`        | UUID      | Yes      | Foreign key → `auth.users.id`                                                                                                            |
| `application_id` | UUID      | No       | Foreign key → `applications.id`. Null for any AI calls not tied to a specific application                                                |
| `request_type`   | Enum      | Yes      | One of: `guideline_summary`, `refine_answer`, `charity_paraphrase`, `draft_generation`, `assemble_draft`. Identifies the type of AI call |
| `token_count`    | Integer   | No       | Total tokens used (prompt + completion). Populated from the Amazon Bedrock API response. Used for cost monitoring                        |
| `created_at`     | Timestamp | Yes      | Timestamp of the request. Used to calculate monthly usage (calendar month window)                                                        |

**Correction (2026-07-10):** this row previously listed `guideline_summary`, `draft_generation`, `charity_paraphrase` and omitted `refine_answer` entirely — meaning the documented enum did not include the value actually inserted by the live `/api/refine-answer` route (`p_request_type: 'refine_answer'`, confirmed in `app/api/refine-answer/route.ts`). Only three of the five DB enum values are written by any live code path today: `guideline_summary` (`/api/generate-summary`), `refine_answer` (`/api/refine-answer`), and `charity_paraphrase` (`actions/charity.ts`). `draft_generation` was written only by `/api/generate-draft`, deleted 2026-07-01 (see `CHANGELOG.md`), and `assemble_draft` has never been written by any route. Both dead values remain in the Postgres enum type — removing an enum value is a separate, riskier migration — so they are listed above for schema accuracy but are not in active use.

**Key constraints:**

- At 40 requests in the current month (80% of 50), a soft warning is shown to the user
- At 50 requests in the current month, AI generation is blocked until the month resets
- This table is permanently deleted when a user deletes their account (FR-43)

**Monthly cap enforcement (corrected 2026-07-13 -- previously described as a simple count-then-insert check, which understated the real mechanism and a bug it was built to fix):** the cap is enforced by three atomic Postgres functions (migration `20260622000002`, a launch-blocker fix for F-01-02), not application-layer counting:

- `reserve_ai_slot(p_user_id, p_application_id, p_request_type, p_monthly_cap, p_approaching_threshold)` -- called **before** the Bedrock call. Uses `pg_advisory_xact_lock` to serialise concurrent calls from the same user, counts the user's rows for the current calendar month, and only if under the cap inserts a placeholder row (`token_count = null`) and returns `{ allowed, log_id, approaching_limit, current_usage }`. The advisory lock exists specifically to close a race condition where two simultaneous requests from the same user could otherwise both pass the cap check before either was recorded (TOCTOU)
- `update_ai_slot_token_count(p_log_id, p_user_id, p_token_count)` -- called after a **successful** Bedrock call, filling in the real token count on the reserved row
- `cancel_ai_slot(p_log_id, p_user_id)` -- called after a **failed** Bedrock call, deleting the reserved row so a service error does not consume the user's monthly allowance

All three are `SECURITY DEFINER`, bypassing the table's INSERT-only RLS policy so the reserve/cancel/update flow can work without granting UPDATE/DELETE to authenticated users directly.

## 6. Inactivity & Deletion

The following fields drive the automated inactivity deletion process (PDR-DH-002):

| Field             | Table                        | Used for                            |
| ----------------- | ---------------------------- | ----------------------------------- |
| `last_sign_in_at` | `auth.users` (Supabase Auth) | Calculating months since last login |

**Process:**

- A scheduled job checks `last_sign_in_at` for all accounts
- At 23 months of inactivity: Email 3 (inactivity warning) is sent
- At 24 months of inactivity (no login after warning): all data for that user is permanently deleted across all tables
- Data deleted: `user_profiles`, `charity_profiles`, `applications`, `application_items`, `ai_usage_log`, and the Supabase Auth user record
- Email 4 (account deleted — inactivity) is sent immediately after deletion completes
